Migrer de VMware vers Proxmox VE : les étapes et les pièges

L'assistant d'import de Proxmox VE rend la copie d'une VM depuis ESXi presque triviale. Ce qui fait échouer une migration se trouve ailleurs : l'inventaire, les pilotes, le réseau, la sauvegarde et le retour arrière. Voici la méthode, étape par étape.

Par Amine, ingénieur DevOps freelance · Mis à jour le 3 novembre 2026

Pour migrer de VMware vers Proxmox VE : inventoriez les VM et leurs dépendances (RVTools), préparez le cluster Proxmox avec le réseau, le stockage et une sauvegarde testée, puis importez les VM par vagues avec l'assistant intégré depuis la version 8.2. Pour chaque VM Windows, installez les pilotes VirtIO avant la bascule. Après l'import, vérifiez le réseau (le nom de l'interface change souvent), installez l'agent invité QEMU, et gardez la VM source intacte jusqu'à la validation.

Avant de toucher à une VM : l'inventaire

Une migration réussie se joue avant la première copie de disque. Commencez par un inventaire complet, que l'utilitaire RVTools produit en quelques minutes depuis vCenter, en lecture seule.

  • Les VM et leurs ressources : processeurs, mémoire, disques, système d'exploitation, version des VMware Tools.
  • Le micrologiciel : BIOS ou UEFI, démarrage sécurisé, vTPM. Une VM UEFI doit le rester côté Proxmox.
  • Ce qui ne se migre pas tel quel : disques RDM, disques partagés entre VM, clusters Windows, VM chiffrées, dépendances à vSAN, NSX ou Horizon.
  • Les snapshots : à consolider avant l'import.
  • Les dépendances applicatives : qui parle à qui, dans quel ordre redémarrer, quelles VM doivent basculer ensemble.
  • La sauvegarde : votre outil doit protéger Proxmox avant la première VM de production. Proxmox Backup Server est une option native.

Préparer la plateforme Proxmox

Installez et configurez le cluster avant d'importer quoi que ce soit : réseau (ponts, VLAN, liens agrégés), stockage (Ceph, ZFS, NFS ou iSCSI selon votre matériel), haute disponibilité, droits d'accès, supervision et sauvegarde. Reproduisez les réseaux de vSphere sous forme de ponts et de VLAN avec les mêmes identifiants : chaque VM importée retrouve ainsi son réseau sans changer d'adresse IP.

Testez ensuite une restauration complète depuis la sauvegarde. Une plateforme dont la sauvegarde n'a jamais été restaurée n'est pas prête à recevoir la production.

L'assistant est la voie la plus simple. Il s'ajoute comme un stockage de type « ESXi » dans le centre de données Proxmox ; les VM de l'hôte apparaissent alors dans l'interface et s'importent une par une. La préversion annonçait la prise en charge d'ESXi 6.5 à 8.0, avec des limites sur vSAN et des performances moindres en passant par vCenter plutôt que directement par l'hôte.

La bascule, VM par VM

  1. Préparer la VM source. Supprimez les snapshots. Pour une VM Windows, installez les pilotes VirtIO et l'agent invité QEMU tant qu'elle tourne encore sur VMware. Notez la configuration IP.
  2. Arrêter la VM côté VMware. L'assistant importe une VM éteinte. Désactivez son démarrage automatique pour éviter qu'elle ne revienne par erreur.
  3. Importer. Choisissez le stockage cible, le type de contrôleur de disque et le pont réseau. Pour une VM Windows sans pilotes VirtIO, démarrez avec un contrôleur SATA.
  4. Démarrer et ajuster. Vérifiez le démarrage, le réseau et l'agent invité. Désinstallez les VMware Tools s'ils sont encore présents. Passez les disques en VirtIO SCSI une fois les pilotes en place.
  5. Tester avec les métiers. L'application fonctionne-t-elle, les flux passent-ils, la sauvegarde de la nouvelle VM a-t-elle réussi ?
  6. Valider ou revenir en arrière. Selon des critères écrits à l'avance. La VM source reste intacte jusqu'à la validation.

Les pièges les plus fréquents

Le nom de la carte réseau change

Sous Linux, l'interface réseau change souvent de nom après la migration (par exemple de ens192 à ens18). La configuration IP ne s'applique plus et la VM démarre sans réseau. Sous Windows, une nouvelle carte apparaît et l'ancienne configuration IP reste attachée à la carte disparue. Prévoyez une console et la configuration IP notée à l'étape 1.

Le pilote de disque manque

Une VM Windows importée directement en VirtIO SCSI sans pilote ne démarre pas. Installer les pilotes VirtIO avant la migration évite le problème ; sinon, démarrez en SATA, installez les pilotes, puis changez de contrôleur.

L'import à chaud mal compris

Le mode d'import « à chaud » démarre la VM sur Proxmox pendant que ses disques sont encore copiés. Si la copie échoue, les données écrites depuis le début de l'import sont perdues. Réservez-le aux VM dont la perte de quelques minutes d'écriture est acceptable, après un test sur une VM sans enjeu.

Les licences liées au matériel

Certains logiciels lient leur licence à l'adresse MAC ou à l'identifiant matériel de la VM. Relevez l'adresse MAC avant l'import et reportez-la si nécessaire ; prévenez l'éditeur si sa licence dépend d'autre chose.

Les dépendances oubliées

Une application qui fonctionne sur trois VM doit basculer en une seule fois. C'est l'inventaire des dépendances, pas la liste des VM, qui définit les vagues.

Organiser les vagues

Commencez par une VM pilote sans enjeu, puis une vague de VM peu critiques, et gardez pour la fin les bases de données et les applications métier. Chronométrez la VM pilote : sa durée réelle sert à planifier toutes les fenêtres suivantes. Gardez l'environnement VMware en état de marche jusqu'à la dernière validation, puis arrêtez-le en vérifiant la date d'échéance de votre contrat.

Questions fréquentes

Combien de temps faut-il pour migrer une VM vers Proxmox ?

La copie dépend surtout du volume des disques, du débit réseau et du stockage. Chronométrez la migration d'une VM pilote représentative : c'est la seule base fiable pour planifier les vagues et les fenêtres d'interruption.

Faut-il désinstaller les VMware Tools avant la migration ?

C'est recommandé. Une fois la VM sur Proxmox, les VMware Tools ne servent plus et leur désinstallation peut devenir plus difficile. Remplacez-les par l'agent invité QEMU (qemu-guest-agent) sur la VM migrée.

Pourquoi ma VM Windows ne démarre-t-elle pas après l'import ?

Le plus souvent, Windows ne dispose pas du pilote du contrôleur de disque choisi. Installez les pilotes VirtIO avant la migration, ou démarrez d'abord avec un contrôleur SATA, puis passez en VirtIO SCSI une fois les pilotes installés.

Peut-on revenir en arrière après la bascule ?

Oui, si vous l'avez prévu : laissez la VM source éteinte mais intacte côté VMware jusqu'à la validation, et notez les données modifiées entre-temps. Le retour arrière se décide sur des critères écrits avant la bascule, pas dans l'urgence.
